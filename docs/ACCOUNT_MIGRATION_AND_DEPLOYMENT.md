# Account migration and deployment

## Prepare and deploy safely

1. Back up Neon and private R2 object keys. Rehearse against a restored staging database. Keep `FORMA_AUTH_REQUIRED=true`, `FORMA_DEMO_MODE=false` and `FORMA_LEGACY_LOGIN_ENABLED=true` in the existing Render deployment.
2. Deploy backend first. It retains existing initialization and runs six reviewed additive migrations under a PostgreSQL advisory transaction lock: `001_public_accounts_course_ownership`, `002_structured_documents_materials`, `003_document_review_history`, `004_durable_email_outbox`, `005_institution_roles`, `006_document_understanding_jobs`. No tables or historical records are dropped. New migrations create only their named tables and record application in `schema_migrations`. Render's existing `uvicorn ... --port $PORT` command is retained.
3. Configure a TLS STARTTLS SMTP service: `FORMA_SMTP_HOST`, `FORMA_SMTP_PORT` (587), `FORMA_SMTP_USERNAME`, `FORMA_SMTP_PASSWORD`, `FORMA_EMAIL_FROM`. Generate a persistent private Fernet key for `FORMA_EMAIL_TOKEN_KEY` using `cryptography.fernet.Fernet.generate_key()`; preserve it across deployments. Set exact HTTPS `FRONTEND_ORIGIN`. Test delivery on staging before setting `FORMA_PUBLIC_REGISTRATION=true`. No email delivery or verification bypass is simulated when SMTP is missing. The feature defaults off. Use an existing transactional SMTP provider; none is purchased or provisioned by this change.
4. Deploy frontend with `FORMA_BACKEND_URL=https://<existing-render-service>` as a Cloudflare Worker runtime binding. Ordinary Node development uses the server environment variable. Existing `NEXT_PUBLIC_API_URL` is a temporary compatibility fallback. Browser requests now use `/api/backend`; the Worker forwards to the configured backend and keeps session tokens in HttpOnly, Secure, SameSite=Lax cookies. Origin checks apply to every mutation, including login. R2 and AI credentials stay on Render. OpenNext's binding access follows its [official documentation](https://opennext.js.org/cloudflare/bindings).
5. Register a verified account for the existing operator. Public registration does not grant educator access or claim historical courses. An operator may explicitly transfer one legacy course with `cd backend && .venv/bin/python scripts/claim_legacy_course.py COURSE_ID VERIFIED_EMAIL`. This command must be run with the intended private database configuration; it refuses unverified accounts and ownership overwrites. It preserves historical relationships and does not import any environment password. Shared legacy teacher access to that course then ends. Record and review each transfer.
6. Leave legacy credentials enabled until all affected people and courses have migrated. Legacy student identifiers and grades are not silently reassigned to newly registered UUID accounts: mapping an existing student's academic identity requires a separate reviewed migration. Do not invent users or infer identity from display names. Disable new legacy logins only after operator access and needed academic mappings are validated.

## Session behavior

Verified accounts use random opaque tokens with only SHA-256 token hashes stored in PostgreSQL. Absolute expiry is eight hours; expiry requires login again rather than a silent renewal. Logout deletes the session; password changes/reset delete all account sessions. Single-use email tokens last one hour and are consumed atomically. Passwords use Argon2id with OWASP's minimum 19 MiB memory profile. See [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Existing stateless legacy bearer tokens keep their original eight-hour expiry during migration. Old sessionStorage tokens may finish this lifetime, but all new browser logins use HttpOnly cookies. Legacy logout clears browser access; unlike account logout, already-copied legacy tokens are not revocable individually. Rotate the old signing secret only during a deliberate cutover because it ends those existing sessions. Never convert plaintext environment credentials into public accounts.

Rate limits are PostgreSQL-backed fixed windows, with per-address and per-identity buckets; counts survive a process restart. They do not trust arbitrary forwarding headers. Through the BFF, outgoing addresses can be shared. Current IP budgets accommodate small classes; production abuse protection should also be configured at Cloudflare. Login uses a dummy password hash for unknown email addresses. Registration and recovery use generic eligibility responses to reduce enumeration. Account discovery paths enqueue encrypted email actions in a durable PostgreSQL outbox, avoiding network delivery timing differences. The small polling thread calls configured SMTP outside requests with a 15-second network timeout, retrying at most three times. Expired worker leases recover after a restart. API responses say queued, not sent. Use `FORMA_EMAIL_WORKER_ENABLED=false` only when running an alternative worker via `email_delivery.deliver_one()`. Outbox tokens are Fernet-encrypted with the dedicated key, then removed after sending/final failure; verification/reset tables contain hashes only. SMTP is at-least-once, so a crash after sending can cause another copy of the same single-use link.

## Storage and document behavior

Documents and materials use the existing private R2 helpers and generated object keys. Extracted document structure is stored in PostgreSQL with a SHA-256 content hash. Upload limits: 30 MB, 50 PDF pages/PPTX slides, 500,000 text characters; OOXML archives are capped by entry count and expanded size. Macros, embedded executables, unsafe paths and XML entity declarations are rejected. DOCX has no reliable page numbers; PPTX visual rendering and presentation delivery evaluation are unavailable. Programming files are UTF-8 static text; ZIPs allow only supported source types, up to 200 entries and 5 MB expanded. Student code is never executed.

Teacher materials default private. Students need active enrollment to list/download visible materials or read their own submission. Review versions are immutable records. Saving a review does not publish a grade. Publication links the selected review to the grade; reassessment preserves earlier review records. Student feedback strips teacher-only reference solutions. Enrollment removal/suspension preserves historical records but removes current student access. Originality still uses bounded same-course lexical comparison; it is not a misconduct verdict and does not cover the web.

## Rollback and external checks

Disable public registration first. Roll back frontend and backend application versions together while retaining additive tables, account records and R2 objects. The previous application will not understand new account sessions; legacy administrator login remains the fallback if still configured. Do not drop account, ownership or review tables as a rollback technique.

Local synthetic tests do not verify live Neon upgrades, SMTP delivery, live R2 or production Cloudflare runtime. Run those staging checks before rollout. No production data, deployment or paid service was changed by the local implementation. Set a retention/deletion policy and obtain jurisdiction-specific advice for Kazakhstan or other deployments; this implementation does not assert legal compliance.


## Phase 3 deployment additions

Review `docs/PHASE3_IMPLEMENTATION_REPORT.md` before rollout. Approve the exact verified operator UUID through `scripts/approve_account_role.py`, then create institutions and approve/invite teachers. Historical owners without an explicit role remain migration-pending for their existing resources; no mass ownership/role conversion occurs. New course creation requires `institution_id` and an active approved membership.

The PostgreSQL document worker defaults to one concurrent job while Render is awake. Optional settings: `FORMA_DOCUMENT_WORKER_ENABLED`, `FORMA_DOCUMENT_CONCURRENCY`, `FORMA_DOCUMENT_JOB_PAGES`, `FORMA_AI_VISUAL_PAGES`, `FORMA_AI_TIMEOUT_SECONDS`. Provider key/model and SMTP settings are reused without rotation. Interpretation is not grading. Original results and teacher corrections are versioned. Rehearse stale lease recovery, quotas, role revocation and invitation delivery before production deployment.

## Submission identifier width migration 007

`007_submission_student_id_width` widens PostgreSQL `submissions.anonymous_student_id` from a shorter VARCHAR to VARCHAR(64), matching the SQLAlchemy model and accepting 36-character account UUIDs. Existing values are preserved. An already expanded VARCHAR(64), wider VARCHAR or unbounded TEXT is left unchanged. The existing transactional advisory lock and `schema_migrations` ledger make repeated startup safe. SQLite needs no width alteration. Backend startup applies this migration; deploy only through the approved release process. No production migration was run during local implementation.
